## 交接目標與範圍

目標是讓新人能用 AI 工具自己重現、定位並修好穩定性問題，修完開 PR 給你審；修不好的才找你。前提是新人要懂 Unity 基礎與專案運作原理，否則不知道該怎麼下 prompt，也看不懂 AI 的回覆。

**交接完成的標準**

- [ ] 能說明專案的運作原理：場景流程、GameManager 與各子系統、資料從哪裡來
- [ ] 能用作弊面板、開發者測試器、Log、Sentry 重現問題並找出出錯的系統
- [ ] 能用 AI 工具修好 bug，並在 PR 中用自己的話說明原因與測試方式
- [ ] 能自己輸出可安裝的 APK，並在手機上驗證修正
- [ ] 能調整現有資料：地圖、事件、角色數值、卡牌（改 Google Sheet → 讀取表單 → 驗證）

**優先順序**

| 順序 | 項目 | 內容 | 狀態 |
| --- | --- | --- | --- |
| 1 | 穩定性 | 當機、卡住、操作上的 bug | 本次交接的重點 |
| 2 | 擴充性 | 新角色、新卡牌、新關卡與地圖 | 暫緩，新人理解專案後再談 |

**待討論**

1. 交接對象有幾位？若多人，是否要分工（例如一位負責修 bug 與發版，一位負責數值）？
2. 交接後由你審 PR 的支援期要多長？問題透過什麼管道問你？

## 新人需要的能力

新人不需要學完整個 Unity，只要學到能指揮 AI、看得懂 AI 回覆就好。用 AI 修 bug 的每一步都需要對應的知識：

| 步驟 | 要會什麼 | 不會的話 |
| --- | --- | --- |
| 1. 重現 | 玩遊戲、用作弊面板與開發者測試器、看 Log | 只能跟 AI 說「會當機」，AI 只能亂猜 |
| 2. 定位 | 知道這個現象屬於哪個系統（戰鬥、地圖、題目、存檔） | 不知道該把哪些檔案丟給 AI |
| 3. 下 prompt | 提供重現步驟、錯誤訊息（stack trace）和相關檔案 | AI 給出很籠統的修法 |
| 4. 判斷回覆 | 看得懂 Unity 的基本概念和 AI 改了什麼 | 照單全收，容易越修越糟 |
| 5. 驗證 | 照原步驟再測一次、上手機測、開小 PR | 修好一個，弄壞另一個 |

**必要的 Unity 知識**（都是判斷 AI 回覆時用得到的）

- GameObject、Component、Inspector 上拖曳的參照（AI 看不到這些設定，很多 bug 出在這裡）
- Prefab、場景切換、DontDestroyOnLoad（GameManager 跨場景常駐）
- MonoBehaviour 生命週期：Awake、Start、OnEnable、OnDestroy
- Coroutine（戰鬥狀態機就是用 Coroutine 寫的）
- ScriptableObject（所有遊戲資料都是）
- Console 的 stack trace 怎麼看、手機上怎麼抓 Log
- Git 分支與 PR

## 時程

交接依過關條件推進，不依日期；等你確定開始日與每週可投入的時間，再幫各階段排上日期。

| 階段 | 內容 | 過關條件 |
| --- | --- | --- |
| 0 | 確認範圍與人選、準備教材 | 範圍與完成標準雙方同意；教材準備好 |
| 1 | 新人事前準備 | 事前準備清單全部勾選，帶著問題清單進入交接 |
| 2 | 知識移轉（4 場） | 4 場完成 |
| 3 | 獨立修 bug | 指定的 bug 都修好，PR 通過你的審查 |
| 4 | 權限轉移與收尾 | 新人用自己的帳號完成一次完整流程 |

階段 1 與階段 0 的「確認新人程度」可以部分並行，其餘階段要依序進行。

## 各階段內容

交接分五個階段，每個階段結束都有一個「過關條件」，沒過就不進下一段。

### 階段 0：確認範圍與人選、準備教材（你與專案負責人）

- 範圍已確定：穩定性優先，擴充性暫緩（2026-10-15）。
- 跟新人確認：人數、Unity 經驗、常用的 AI 開發工具、使用 Mac 或 Windows。
- **過關條件**：交接範圍與完成標準有寫下來，雙方同意；下方教材準備好。

**你要準備的教材**（做一次，所有新人都受益）

- [x] **bug 清單**：初稿完成（2026-10-15），見 [BugList.md](BugList.md)。從程式碼找出 8 個問題並依難度分級，**都還沒實機重現**，交接前要先逐一重現並更新狀態。同時是階段 2 的教材與階段 3 的題目；拿到 Sentry 錯誤或已知 bug 後再補進來。
- [ ] **`CLAUDE.md` / `AGENTS.md`**：放在 repo 根目錄，寫專案架構與禁止事項（列舉值只能往後加、改存檔結構要處理版本轉換、Inspector 的參照 AI 看不到）。不論新人用 Claude、OpenCode 或 Kilo，AI 一開始就能讀到。
- [ ] **修 bug 的 prompt 範本**：固定填「現象、重現步驟、錯誤訊息、懷疑的系統」，並加上「先解釋原因，不要直接改」。
- [ ] **PR 範本**：重現步驟、用自己的話寫的原因、怎麼測過的。寫不出原因就不能送出；你審 PR 時主要看這段。

**方案：新人的 Unity 程度不足時**

| 方案 | 做法 | 優點 | 缺點 |
| --- | --- | --- | --- |
| A. 先自學再交接 | 指定 Unity Learn 的基礎課程，完成後再開始 | 你花的時間最少 | 拉長整體時程 |
| B. 只教「修 bug 用得到的」（建議） | 只教上方「必要的 Unity 知識」，其餘遇到再問 AI | 最快上手，內容都和實際工作有關 | 遇到範圍外的問題會卡住，要靠 AI 或問你 |

### 階段 1：新人事前準備（自行完成）

給新人的說明與學習資料：[新人入門指南](Onboarding.md)（[線上版](https://claude.ai/code/artifact/52792cc8-7b7b-4ccf-9f5f-11f977c46784)）。

- [ ] 完成 Unity Learn 的 Essentials 入門課程前幾個單元，會操作編輯器即可
- [ ] 安裝 Unity 2021.3.30f1，**包含 Android Build Support 模組**（輸出 APK 必需）
- [ ] Clone 專案並能正常開啟、從主選單按 Play
- [ ] 有自己的 AI 開發工具（Claude、OpenCode、Kilo 等）
- [ ] 至少玩過並通關一次遊戲（可用作弊面板加速，重點是走完整個流程）
- [ ] 讀過 `Docs/Handover.md`，並用 AI 工具請它介紹專案，寫下 3 個看不懂的地方

**過關條件**：以上全部勾選，帶著問題清單進入面對面交接。

### 階段 2：知識移轉（4 場）

先教專案與工具，再示範修 bug，最後讓新人自己修。第 3 場最重要：新人最缺的是判斷 AI 回覆的能力，這只能看你示範來學。

| 場次 | 主題 | 誰操作 | 內容 |
| --- | --- | --- | --- |
| 1 | 專案運作原理 | 你 | 從主選單玩一輪，每到一個畫面說明是哪個場景、哪個 Manager、資料從哪來。最後練習問 AI「X 功能在哪裡處理」並一起確認答案 |
| 2 | 除錯工具 | 新人 | Console 的 stack trace、開發者測試器、作弊面板、匯出 Log、Sentry、手機 logcat、Git 分支與 PR |
| 3 | 示範修 bug | 你 | 用 AI 修 B1（效果佇列卡死），邊做邊說：為什麼這樣下 prompt、AI 哪句可以信、為什麼拒絕「只加 null 檢查」的修法 |
| 4 | 帶著修 bug | 新人 | 先用 B7 暖身走一次完整流程，再修 B3（答題卡住）；你只在卡住時給提示，不接手 |

**要提醒新人的 AI 陷阱**

- AI 常到處加 null 檢查：當機不見了，但真正的原因被藏起來。
- AI 會想直接改 `.unity`、`.prefab` 檔，容易把參照弄壞；這類修改要在 Unity 編輯器裡做。
- 電腦上正常不代表手機上正常，效能與當機一定要上手機測。

**提案**

- 每場錄影，後續新人（或再下一任）可以重看。
- 文件目前分散在 HackMD、Milanote、Google Sheet 與 repo 內。建議以 `Docs/Handover.md` 為唯一入口，其他文件只放連結，避免新人不知道該信哪一份。

### 階段 3：獨立修 bug（新人完成，你審 PR）

新人從 bug 清單挑題目自己修。可以問你方向，但重現、修改和測試由新人完成。

- [ ] 從 bug 清單修好 3 個 bug（簡單、中等、困難各一，建議 B6、B4、B2），各開一個 PR
- [ ] 每個 PR 都寫了重現步驟、用自己的話寫的原因、怎麼測過的
- [ ] 修好的版本輸出 APK，安裝到手機並重現原本的操作，確認問題不再發生
- [ ] 改一張卡的數值，讀取表單，在遊戲中看到變化

**過關條件**：全部任務完成，PR 都通過你的審查。練習用的變更做在獨立分支，審查通過再合進 main。

### 階段 4：權限轉移與收尾

| 項目 | 要做的事 |
| --- | --- |
| GitHub Repo | 加新人為 collaborator；考慮是否要轉到組織帳號 |
| Google Sheet 配置表 | 給編輯權；考慮轉移擁有權 |
| eMath 題庫 API | 介紹新人給題庫端窗口，確認 Token 是否要更換 |
| Sentry | 加入專案成員 |
| 付費套件 | 確認 Odin、Easy Save 3、Feel、Cartoon FX 的授權是否包含新人 |
| Android 簽章金鑰（Keystore） | 目前專案沒有設定，見下方待討論 |
| 上架帳號 | 若有 Google Play 開發者帳號，要加入新人 |

**過關條件**：新人用自己的帳號完成一次「修 bug → 開 PR → 合併 → 輸出 APK」，全程不用你的帳號。

**待討論：APK 要怎麼發佈？**

專案目前沒有自訂 Keystore，輸出的 APK 用的是每台電腦各自的 debug 簽章，Android 的 Application Identifier 也未設定。

| 方案 | 適用情境 | 需要做的事 |
| --- | --- | --- |
| A. 維持 debug 簽章 | 只在校內或活動中直接安裝 APK | 不同人輸出的版本無法直接覆蓋安裝，要先移除舊版 |
| B. 建立正式 Keystore | 有對外發布或要上 Google Play | 建立 Keystore、設定 Package Name、以密碼管理工具保存；遺失後無法再更新同一個 App |

## 風險與待決事項

最大的風險是「只有你知道」的東西：帳號、金鑰與沒寫下來的經驗，這些應該在你離開前全部轉移或文件化。

| 風險 | 影響 | 建議做法 |
| --- | --- | --- |
| 帳號與資料在你個人名下（GitHub、Google Sheet、Sentry） | 你離開後新人無法管理權限 | 轉到單位共用帳號或組織，或至少再加一位管理者 |
| 新人照單全收 AI 的修改 | 症狀被掩蓋，或修好一處弄壞另一處 | PR 必須寫出原因與測試方式；你審 PR 時先看這段 |
| 沒有自動化測試 | 新人改程式容易弄壞戰鬥 | 整理一份「發版前手動測試清單」，每個 PR 都照著測 |
| 題庫 API Token 寫死在程式且在 Git 歷史 | 有 repo 存取權的人都能使用 | 交接前跟題庫端確認是否更換 |
| 文件分散且可能過時（HackMD、Milanote） | 新人照舊文件操作出錯 | 以 Docs/Handover.md 為主，檢查舊文件後標註「已過時」或整併 |
| 付費套件授權不明 | 新人使用可能違反授權 | 確認購買者與授權條款 |
| Android 發布設定未完成（無 Keystore、無 Package Name） | 版本無法覆蓋安裝、無法上架 | 在階段 4 定案發布方式 |

**需要你回答的問題**

1. Milanote 的程式交接文件與 Docs/Handover.md 是否有重疊？要整併還是各自保留？
2. 交接預計何時開始、何時結束？你在交接期間每週可以投入多少時間？
3. 最終版是否要上架 Google Play？若要，應該在交接前由你建立 Keystore 與 Package Name。
4. 交接後的支援期要多長？問題與 PR 透過什麼管道給你？
5. 有沒有 Sentry 錯誤紀錄或已知的 bug 清單可以當作 bug 清單的來源？
